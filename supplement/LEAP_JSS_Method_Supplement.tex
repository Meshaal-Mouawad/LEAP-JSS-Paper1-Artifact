\section{Input, routing, and candidate order}
The entry point is \code{find_kpis_in_directory} in \code{software/LEAP/bluebook_generator/kpi_extractor.py}, lines 1194--1449. An initial inventory and the subsequent filtered traversal are separate passes. The second uses \code{os.walk} without sorting directory or filename lists. Hidden/configured directories, configured filenames, and binary extensions are excluded before candidate selection. The default allowed-extension set and exclusions are at lines 5--98; language hints and the dispatcher are at lines 150--182 and 1160--1191. The allowed-extension set is a separate gate from the hint map: an extension's presence in the latter does not alone ensure that default scanning includes it.

\code{KPI_SCAN_ALL} accepts \code{1}, \code{true}, or \code{True} to permit otherwise unsupported text-like extensions. Such files use the generic route. \code{KPI_MAX_FILE_MB} defaults to 2 and supplies a size gate in MiB; the safe reader also has its own 2,000,000-byte limit. Thus the environment setting alone does not remove that reader bound. Empty or unreadable text produces no candidate. The suffix-hint loop returns its first match; exact matching order is part of the frozen implementation.

The language route is attempted first, followed by generic patterns only when no candidate was produced. If neither supplies a candidate, the scanner may construct a rank-0 logic fallback; optional \code{KPI_FORCE_FILE_FALLBACK} enables a rank-$-1$ fallback. These fallbacks are subsequently withheld by the promotion gate. The helper \code{_extract_logic_heuristics} also contains a rank-0 constructor, but is not called by this entry point. Its presence is not evidence of an additional exercised path.

Candidate emission order follows extractor pass order, then source-line order within a pass. Examples include: Python comments before function-name candidates; .NET attributes before slash comments, apostrophe comments, and method names; SQL comments before fallback passes; and DAX defined measures before simple measures and KPI comments. Generic extraction has four comment-style passes, followed by its block/bare-line pass. HANA uses SQL-like candidates first and only then a JSON-column fallback. PL/SQL likewise attempts SQL-like candidates before its package-signature fallback. No global sort merges these route-local sequences.

\section{Promotion predicates and context boundaries}
\code{evaluate_candidate_promotion} (lines 412--590) returns at the first applicable branch. The following order is significant:
\begin{enumerate}[leftmargin=*,nosep]
\item Withhold scenario fixtures during an ordinary repository scan; the dedicated scenario-directory scan is an explicit exception.
\item Reject matching invalid/test/mock/debug names; empty, shorter-than-three-character, or generic \code{kpi} names; embedded newlines/code keywords; names over 120 characters; and names containing braces or semicolons.
\item Compute explicit-marker, formula-marker, business-metadata, and calculation predicates. Reject strict helper-name matches lacking an explicit KPI marker.
\item Withhold weak kinds: \code{logic_fallback}, \code{forced_fallback}, \code{empty_file_fallback}, and \code{plsql_return_fallback}.
\item For CSV, require explicit KPI and Formula evidence and no bad-formula artifact. This branch returns before the general explicit/inferred branches.
\item For explicit candidates, require at least one of a formula marker, calculation evidence, or business metadata.
\item For the nine medium inferred kinds (Python function, .NET method, SQL alias/function/view, PL/SQL function, HANA JSON, simple DAX, ABAP REPORT), require business context, business-shaped formula structure, and executable-calculation evidence. Python/function-method kinds additionally require local return arithmetic.
\item For other kinds, accept business context plus calculation structure, or explicit metric-language wording plus calculation structure. Otherwise retain an Extraction Review reason.
\end{enumerate}

All predicates are textual rules. They are not an AST-level proof that an expression is executable or that a named aggregate is a business KPI. Table S1-B points to the precise tests; the supplied excerpts contain their exact regular expressions and vocabulary.

\textbf{Context windows.} The shared \code{_window} uses up to 10 preceding and 20 following lines, plus the anchor line. .NET attributes and methods use 5/60; SQL view candidates use 5/120; SQL alias candidates use 3/80. PL/SQL explicit comments use 0/160. SQL comments in other dialects and SQL function fallbacks use \code{_expand_forward_statement}: up to five preceding lines and at most 200 lines from the anchor, stopping at a trailing semicolon at nonpositive tracked parenthesis depth, a lone GO, a lone slash, or end of file. Exact bounds and terminator expressions are at lines 202--244 and their call sites in the locator index.

HANA JSON fallback constructs \code{SELECT <expression> AS <name>} and assigns anchor 1; it does not recover an original source span for that constructed text. The PL/SQL-return fallback retains the whole file, then fails the weak-kind promotion gate. Scanner logic/forced fallback contexts keep at most the first and last 4,000 characters when the input exceeds 8,000 characters; those kinds are also withheld. Context windows are neither full dependency slices nor guarantees that all null/guard behavior is represented.

\textbf{Dossier-stage context.} These are extraction-time windows. In \code{main.py}, \code{create_rst_file} reloads the source file when readable (1469--1488), otherwise using captured context. Python then passes that text and its anchor to \code{_extract_function_block} (506--558; 1490--1501); the helper retains the original text when no function is located. Other formats use all available text (1502--1504). Thus the formula parser need not receive the original extraction window, and declaration comments may remain in its input.

\section{Normalization, duplicate retention, and residual ties}
\code{_normalize_name} (247--256) strips surrounding whitespace and one matching outer pair among brackets, parentheses, single quotes, and double quotes. Otherwise it strips outer quote characters; underscore/whitespace runs collapse to one space. It does not lowercase the result.

After promotion, within-file deduplication retains the first candidate for each exact name; subsequent candidates with that name are discarded before rank selection (1393--1401). Selection then uses \code{max} over (rank, readable-name flag), where the flag tests for a space, parenthesis, or square bracket (1407--1416). Residual ties retain the first encountered candidate. The cross-file exact-name set likewise keeps the first selected occurrence (1445--1447). No sorting step makes this order-independent.

DAX performs additional earlier lowercase-name suppression in its defined-measure/simple-measure/comment passes (936--997). The comment pass consults that set but does not add new comment names to it; final exact-name deduplication still applies. HANA's JSON fallback keeps the earlier column on equal local scores. These route-local decisions precede the common selection procedure and must not be silently replaced by a universal case-insensitive deduplicator.

\section{Formula preparation, conflict rules, and rendered status}
\code{generate_formula_from_code} in \code{bluebook_generator/main.py} (561--1428) prepares formula-like text, not exclusively executable expressions. \code{extract_calculation_hint} (1101--1135) scans comment labels Formula, Business Formula, Body hint, Body computes, Computes, and Calculation. In encounter order, invalid candidates are skipped; the first math-like hint is returned. \code{extract_result_name_and_expression} gives a suitable hint precedence (1202--1208), then tries NPS and structured-expression rules (1212--1218), followed by SELECT, assignment, return, and fallback paths. A hint name without an expression does not terminate extraction. The main call uses the unfiltered context (1408--1411); construction of cleaned lines at 1185--1191 does not remove comments from this call.

The normalization helper (648--663) removes selected SQL wrappers for display, not for semantic equivalence. Explicit LaTeX preservation/normalization is at 250--489. Declared text can also originate in \code{parser.py} (4--12). The downstream context transition in S1.3 precedes preparation of \code{programmatic_formula} (1490--1504). A formula-like \code{formula_description} is processed separately (1614--1661); these two paths can reuse declaration evidence rather than establish independent executable and declared formulas.

\textbf{Exact display-quality rule.} \code{_formula_html_quality} (1632--1651) substitutes an empty string for falsy input and returns 0 only when that string is empty or contains the case-sensitive literal \verb|See code context|. Otherwise it starts at 2; it subtracts 1 once if any of \code{Placeholder}, \verb|= 0.0|, \code{Nullif}, \code{\text{Count}}, \code{\text{Cast}}, \verb|\text{Date Difference}|, \code{\text{Number}}, or \code{\text{Return}} occurs; it adds 1 once if \code{\frac} or \code{\times} occurs. The note emitted by \code{_missing_formula_html} (464--470) has none of these markers, so it scores 2, not 0. A literal \code{Placeholder} alone scores 1. This is a display-selection heuristic, not a formula-validity score.

The declared display is preferred when its quality is at least the programmatic display's quality, or a mismatch is found (1729--1730). Explicit LaTeX in the record has a later normalization/display path (1740--1764); selected template output and fallbacks are at 2690--2805. Display preference does not establish semantic authority.

The mismatch predicate (1653--1730) compares addition-or-subtraction, division, and multiplication families. Programmatic HTML contributes operator cues (1662--1671). A separate textual scan skips blank lines and lines starting with \code{--}, \code{#}, \code{//}, \code{'}, or \code{*}, removes arrow-type symbols, and collects operators (1672--1692). Their union is \code{evidence_ops} (1693). A formula-like declaration with positive display quality and operator symbols triggers mismatch if one declared family is absent from that union (1694--1705). Skipping comments in the textual scan does not remove declaration-derived operators already present in the programmatic display. Declaration reuse can therefore suppress a mismatch. The cues are not invariably independent executable evidence. The Gross Margin Python example still has the stated mismatch: its function-scoped ratio lacks the declared addition/subtraction family. The predicate also cannot generally distinguish addition from subtraction, arbitrary variable identities, operand order, or whole-program equivalence.

The rendered review label uses ordered conditions (2631--2690): a formula mismatch, governance conflict, audit note, or compliance alarm yields \emph{Needs Review}; otherwise an approved override yields \emph{Validated}; otherwise a numeric score below 75 yields \emph{Needs Review}; otherwise \emph{Validated}. Malformed scores fall back to 0. An override does not bypass the conflict branch. This label differs from intermediate governance status (1584--1606) and the prepared-record harness's derived status; none is external certification.

Token helpers are at 2228--2478. The token strip is not a grouping-preserving equation; formal mathematics and captured source remain separately inspectable.
